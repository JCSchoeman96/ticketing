## 1. Amendment purpose

This version incorporates two technical decisions discovered while implementing/reviewing TICK-25:

1. the secure Ash/AshPostgres baseline required by the repository security gate; and
2. the explicit TEN-1 exception governing the three TICK-25 tenant-resource physical UUIDv7 primary keys.

The trusted organizer proof, authorization, Event lifecycle and transaction boundary remain unchanged.

## 2. Governing invariants retained

The T0-01 trusted organizer boundary remains:

```text
candidate org selector
→ membership proof
→ post-proof User/Session/role liveness
→ persisted organization persona
→ IAM-1 capability authorization
→ draft Event insert
```

The integrated effect MUST use one outer `Ash.transact/3`.

Before membership proof, the only permitted tenant business-row access is the matching OrgMembership probe.

After proof, User, Session and active RoleAssignment must independently satisfy canonical liveness and consistency rules. The same PostgreSQL transaction and tenant context must continue through Event creation.

No reusable completed-transaction organizer persona is produced.

Unexpected Ash-generated schema, migration or snapshot drift is a stop condition.

## 5. Tenant-resource physical PK exception

TEN-1's explicit narrow exception is selected for exactly:

- `identity_org_memberships(org_membership_id)`
- `identity_sessions(id)`
- `identity_org_role_assignments(role_assignment_id)`

Each excepted PK must satisfy all of these conditions:

1. generated by database `uuidv7()` in production;
2. non-writable through production Ash interfaces;
3. never client/caller supplied in production;
4. not usable as a global authorization or tenant-selection mechanism;
5. still subject to correct tenant context and RLS;
6. not exposed as a tenant-visible uniqueness oracle.

The test-only owner fixture may inject deterministic identifiers and does not constitute a production client boundary.

No other tenant resource inherits this exception.

## 6. Tenant index invariants

The physical-PK exception does not change tenant identity isolation.

The following org-first unique indexes are mandatory:

- `identity_org_memberships`: `(org_id, org_membership_id)`
- `identity_org_memberships`: `(org_id, user_id)`
- `identity_org_role_assignments`: `(org_id, user_id, role)`
- `identity_sessions`: `(org_id, id)`

Tests must inspect PostgreSQL catalog metadata and prove exact column ordering, not merely textual/sub-string presence in index definitions.

## 7. Foreign-key invariant

The single-column physical-PK exception does not authorize ID-only tenant relationships.

Any future tenant-to-tenant relationship involving an excepted resource identifier must preserve the tenant dimension required by TEN-1. A UUID's global uniqueness must never substitute for tenant ownership proof.

## 8. Collision-observability invariant

TICK-25 has no tenant-facing production create path for Membership, Session or RoleAssignment PKs.

Accordingly, T0-01 does not manufacture a collision/audit protocol for a boundary that cannot presently be exercised.

If future production work permits creation, issuance, import, mutation, replay or another operation through which PK uniqueness could be observed, that work must stop and re-Grill TEN-1's masked-and-audited exception requirement before exposing the boundary.

If the exception predicates cannot be proven during final review, do not silently assume the exception; stop and re-Grill a composite-PK design.

## 9. Session boundary

Session remains read-only for T0.

The application does not:

- issue a Session;
- refresh it;
- rebind it;
- revoke it;
- mutate `last_seen`;
- emit Session lifecycle events;
- receive, read, compare, derive or return raw token/token_hash.

Authentication/session infrastructure supplies the authoritative `session_id`.

## 10. Organizer authorization boundary

Authoritative identity inputs:

- `user_id`;
- `session_id`.

Caller selectors:

- candidate `org_id`;
- `active_scope`;
- `active_role`.

The caller cannot make an organization authoritative merely by selecting it. Membership proof establishes the organization.

IAM-1 remains the authority for `evt.event.create`. Only canonical permitted human organizer roles may satisfy the capability. Platform/support personas cannot satisfy the tenant capability. IAM-2 does not grant Event-create authority.

## 11. Identity resource/interface boundary

`Ticketing.Identity` owns:

- global `User`;
- tenant `OrgMembership`;
- tenant read-only T0 `Session`;
- tenant `OrgRoleAssignment`.

TICK-25 exposes only governed reads/probes required later by the integrated Event transaction. It does not expose production setup, issuance, grant, activation, create, update or destroy convenience interfaces for these T0 tenant resources.

The narrow owner/test fixture boundary may seed pre-existing state and must remain unavailable as a production domain shortcut.

## 12. RLS boundary

Tenant Membership, Session and RoleAssignment remain protected by the existing transaction-local tenant-context substrate and FORCE RLS.

Required negative behavior includes:

- no tenant context → no tenant-row exposure;
- wrong tenant context → no other-tenant row exposure;
- global UUID alone → insufficient for row access;
- cross-tenant existence → hidden as governed.

The constrained runtime role remains the relevant RLS proof environment.

The candidate `org_id` may authorize only the TEN-1 matching membership probe before proof. The same UUID remains in transaction-local context after proof; there is no second tenant-context transition.

## 13. Event boundary

The downstream `create_event` action remains unchanged from v0.1.3.

It creates one canonical tenant-owned draft Event only after organizer proof and IAM authorization.

Required initial invariants include:

- action-generated UUIDv7;
- action-generated public event key;
- proven tenant ownership;
- draft status;
- publication timestamp absent;
- initial version and lock-version values;
- protected fields not caller-authored;
- database-owned timestamps;
- canonical tenant uniqueness and duplicate-race behavior.

No occurrence, publication, commerce, payment or admission behavior is added by this amendment.

## 14. Transactions, races and replay

The integrated organizer/Event operation remains one outer transaction.

The implementation must prove:

- membership probe occurs before other tenant business reads;
- the PostgreSQL backend transaction remains continuous;
- the proven organization does not change mid-operation;
- tenant context does not leak after commit;
- tenant context does not leak after rollback;
- tenant context does not leak after exception;
- pooled connection reuse does not retain tenant context.

The PK exception introduces no new idempotency or replay semantics. Database constraints remain authoritative for uniqueness races.

Do not invent stronger concurrent Session/role-revocation linearization than canonical authority requires.

## 15. Errors, events, jobs and observability

ERR-1 remains governing error authority. No new canonical error is introduced.

Cross-tenant and unauthorized behavior must preserve information hiding.

TICK-25 and TICK-54 emit no new domain event or outbox record and introduce no background job.

Observability must not expose raw `org_id`, `user_id`, `session_id`, credentials or token hashes in telemetry labels/logs.

## 20. Stop conditions

Stop affected implementation if:

- canonical authority changes materially;
- ROADMAP/tracer changes materially;
- the secure dependency combination changes transaction/authorization/tenant semantics;
- codegen introduces unexpected database changes;
- any TEN-1 exception predicate fails;
- a production caller can supply an excepted PK;
- PK uniqueness becomes tenant-observable without governed masking/audit;
- a tenant relationship attempts ID-only linkage;
- TICK-25 requires downstream Event behavior;
- a locked decision becomes stale.

## 21. Non-goals
