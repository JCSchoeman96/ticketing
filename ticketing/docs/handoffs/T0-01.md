## Implemented Event-create boundary

`Ticketing.Events.create_event/2` is the production entry point. The Event resource exposes one create capability, `create_event`. Its complete effect runs in one outer governed `Ash.transact/3`:

```text
candidate org selector
→ Membership proof
→ User liveness
→ Session liveness using database UTC
→ RoleAssignment liveness
→ persisted-evidence organization-persona validation
→ IAM evt.event.create authorization
→ Event insert
```

Membership proof is the first tenant business-row read. The caller's candidate `org_id`, scope and role are selectors until persisted evidence validates them. Session and role must be active and non-revoked; Session expiry uses database UTC. The persisted evidence and trusted actor are validated within the current orchestration. No reusable authorization credential or persona results from that check.

There is no `persist_draft` or equivalent second Event persistence action. A fabricated organizer/persona map alone cannot pass the complete proof. Event persistence remains authorized; the implementation does not use `authorize?: false`, and Events does not duplicate IAM role or capability policy.

## Persisted state and lifecycle

The merged `events` table has tenant-composite primary key `(org_id, event_id)`. The governed action generates the Event UUIDv7 and derives the public event key. The database enforces tenant-scoped uniqueness for `(org_id, public_event_key)` and `(org_id, slug)`. A newly created Event has `status = draft`, `published_at_utc = nil`, `version = 1`, and `lock_version = 1`. UTC creation and update timestamps are database-owned. Tenant and Event identifiers, public key, status, lifecycle timestamps and version fields are protected from caller writes. The create action does not provide arbitrary lifecycle mutation.

## Tenancy, RLS and transaction evidence

The outer transaction installs candidate `org_id` in transaction-local `app.current_org_id` so RLS can expose the matching Membership probe. Before that proof succeeds, the candidate remains only a selector. After proof, the same UUID remains in the setting through the other persisted evidence, IAM authorization and Event insert.

TICK-28's continuity test observes the Membership query and Event INSERT through Repo query telemetry. At each stage it reads `pg_backend_pid()` and `current_setting('app.current_org_id', true)`. Both observations report the expected organization UUID and the same backend PID. The test observes one tenant-context `set_config` transition for the integrated create.

The tenant tables use `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`, with `USING` and `WITH CHECK` tenant policies. TICK-28's direct-SQL test reads Membership, Session and RoleAssignment rows across tenant context; those reads return no rows, including when the caller knows globally unique physical UUIDs. Its write probes target Event rows: updating another tenant's Event affects zero rows, and changing an Event's `org_id` is rejected by RLS. The test does not attempt Identity-table writes, so their `WITH CHECK` policies describe structural enforcement rather than direct TICK-28 write evidence. Tests also check that the runtime role is not the table owner or a superuser and has `NOBYPASSRLS` posture. Globally unique physical UUIDs do not grant tenant access.

TICK-28 verifies that transaction-local context is absent or empty after successful commit, proof rollback and exception, then checks pooled-backend reuse without tenant bleed. Failed proof leaves no Event and does not mutate Session state. Database uniqueness constraints own duplicate/concurrent uniqueness outcomes. The increment adds no stronger concurrent Session/role revocation linearization and no generic Event-create idempotency/replay contract.

## Errors, events and observability

ERR-1 remains the governing error authority; cross-tenant information hiding is preserved. Draft Event creation emits no publication event, outbox row or job. Raw organization, user and session IDs, credentials and token hashes must not appear in logs or metric labels. TICK-28 adds integrated success/failure evidence that inspects emitted metric labels and production-level log output for sensitive sentinels. These tests add no production logging or telemetry behavior.
