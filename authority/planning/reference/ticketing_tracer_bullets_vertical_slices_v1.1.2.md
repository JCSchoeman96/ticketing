## 1. Source anchors and constitutional constraints

V42 v1.3 is the constitutional layer: it defines non-negotiable rules, not UI features. Feature-specific behaviour belongs in downstream contracts and feature packs. V42 v1.3 also introduces FR-1 as the planning surface for future capabilities, confirms seating and dynamic pricing as governed subsystems, and preserves the money, tenancy, observability, inventory, and order snapshot invariants.

The platform must preserve these non-negotiables:

- double-entry immutable journals,
- idempotent money operations,
- no recomputation of historical prices,
- payout blockers on integrity violations,
- inventory as truth,
- time-bounded and versioned seat holds,
- immutable order price snapshots,
- `org_id` on every write path,
- Postgres RLS with transaction-local tenant injection,
- Oban-only retries for side effects,
- circuit breakers and degraded modes that preserve correctness,
- observability gates for payouts and release actions.

V42 explicitly names these governed subsystem contracts as extension points: **SEAT-1, PRICE-1, ORD-1, OBS-1, PSC-1, OBQC-1, DMSC-1**.

### 1.1 CMS/editorial boundary

V42 v1.3 lists **CMS / Editorial tooling** as a deferred non-goal. Therefore this planning document uses the following safe boundary:

- Allowed: **event-specific sales content required to sell tickets**.
- Not allowed in MVP: a general CMS, editorial publishing platform, meeting-notes system, or broad content workflow.

Accordingly, v1.1 renames:

- `VS-030 Event template/content creation` → `VS-030 Event sales content baseline`.
- `VS-031 Event editorial workflow` → `VS-031 Event publish approval workflow`.


### 1.2 Canonical finance resource names

Use only the canonical finance resource names in feature packs and coding prompts:

- `Account`
- `JournalEntry`
- `LedgerLine`

`JournalEntry` is canonical. `LedgerJournal`, `Journal`, `AccountingEntry`, `LedgerEntry`, and similar aliases MUST NOT be introduced unless a future contract explicitly defines them.

## 2. Classification system

The v1.0 document mixed true tracer bullets, vertical slices, shared primitives, governance gates, future features, and ops readiness work under one umbrella. v1.1 fixes that with a classification column.

| Class | Meaning | Coding-agent handling |
|---|---|---|
| `TB` | True tracer bullet. Small high-risk proof through the real stack. | Build only after dependencies and gates are known. |
| `VS` | User/business vertical slice. Full feature path. | Must become a Feature Planning Pack before coding. |
| `PP` | Platform primitive. Shared law/utility used by many slices. | Build early; downstream slices must not reinvent it. |
| `CI` | Governance/test gate. Enforced by CI/lint/property tests. | Implement before dependent feature work. |
| `OPS` | Operational readiness slice. Reliability, observability, incident, release, load, runbooks. | Build alongside features, not after launch. |
| `FUT` | Deferred/future feature. Valuable but not MVP unless explicitly pulled forward. | Keep in FR-1 with deferred reason. |


### 2.0A Class and ID authority

For v1.1.2, the **Class column is authoritative**. The ID prefix is a stable historical planning handle and MUST NOT be used by automation to infer class.

Reason: v1.0/v1.1/v1.1.1 already created cross-references using `TB-*` and `VS-*` handles. Renaming every mismatch now would create churn, break review continuity, and risk accidental duplicate IDs. Feature Planning Packs may later introduce clean `FP-*` IDs without changing the historical catalogue rows.

Planning-lint therefore validates the explicit `Class` cell, not the ID prefix.


### 2.1 Release phase and MVP blocker values

v1.1.2 replaces the blunt `Release classification` signal with two separate planning fields.

| Field | Value | Meaning |
|---|---|---|
| `release_phase` | `foundation` | Must exist before real feature work can safely begin. |
| `release_phase` | `sell_scan_reconcile_mvp` | Part of the first production sell → scan → reconcile path. |
| `release_phase` | `enterprise_hardening` | Required before serious production scale, multi-org operations, or finance/support maturity. |
| `release_phase` | `conditional` | Needed only if the related business capability is pulled forward. |
| `release_phase` | `future` | Intentionally deferred; keep in FR-1 with a deferred reason. |
| `mvp_blocker` | `yes` | Blocks the first safe MVP sell/scan/reconcile release. |
| `mvp_blocker` | `no` | Does not block the first safe MVP release, even if important later. |

**Rule:** `release_phase = sell_scan_reconcile_mvp` does not automatically mean “build immediately.” It means the row belongs inside the first production spine once its prerequisites and Feature Planning Pack are resolved.

## 5. Feature Planning Pack template

Every row in this document must be expanded into this structure before coding starts.

| Field | Required content |
|---|---|
| `feature_pack_id` | Stable ID, e.g. `FP-TB-009-seat-hold-race` |
| `source_row_ids` | TB/VS/PP/CI/OPS rows included |
| `classification` | `TB`, `VS`, `PP`, `CI`, `OPS`, or `FUT` |
| `FR_ref` | Feature Registry reference; `FR-TBD` is not acceptable for coding |
| `governing_contracts` | Contract IDs and versions used as authority |
| `candidate_resources` | Possible Ash resources and DB tables touched; not automatically authoritative |
| `definitely_required_resources` | Narrowed resource list required for coding; must not be `TBD` in coding-ready packs |
| `candidate_actions` | Possible Ash actions, commands, queries, jobs, tasks; not automatically authoritative |
| `definitely_required_actions` | Narrowed action list required for coding; must not be `TBD` in coding-ready packs |
| `state_groups` | Canonical state machines touched |
| `policies` | Actor/tenant/capability rules |
| `db_constraints` | Unique constraints, FK constraints, checks, indexes, RLS rules |
| `idempotency_keys` | Required keys and uniqueness scope |
| `audit_events` | Audit event names, required fields, reason requirements |
| `telemetry` | Metrics, spans, logs, SLOs, alert hooks |
| `error_codes` | Stable error codes from registry |
| `oban_jobs` | Queues, uniqueness, retry, backoff, quarantine behaviour |
| `acceptance_tests` | Positive, negative, race, retry, and tenant-leak tests |
| `must_have_gates` | CI/test gates that block merge/release |
| `blocked_by` | Upstream dependencies |
| `blocks` | Downstream slices blocked by this work |
| `non_goals` | Explicit exclusions to prevent scope creep |
| `release_phase` | `foundation`, `sell_scan_reconcile_mvp`, `enterprise_hardening`, `conditional`, or `future` |
| `mvp_blocker` | `yes` or `no` |
| `definition_of_done` | Evidence required before pack is accepted |

## 9. Overlap map for efficient development

### Overlap 1: Actor context, tenant context, and policy checks

Touches: auth, orgs, admin portal, sales, finance, scanning, exports, marketing.  
Shared primitive: `ActorContext`, `TenantContext`, correlation ID, policy helpers.  
Rule: no process dictionary “current_org”; every action receives explicit tenant and actor context.

### Overlap 2: Audit events

Touches: event publish/cancel, seat map change, refund, payout, transfer, scanner assignment, export, impersonation.  
Shared primitive: append-only audit writer with standard fields.

### Overlap 3: State machines

Touches: EventOccurrence, PaymentIntent, Order, Ticket, Refund, Payout, Transfer, Subscription, Export, ScannerAssignment, WebhookReceipt, ReconciliationRun.  
Rule: no raw status updates outside approved transition actions.

### Overlap 4: Idempotency

Touches: webhooks, payment success, ticket issuance, ledger posting, refunds, payouts, notification sending, exports, scan sync.  
Shared primitive: idempotency key registry and DB-backed uniqueness.

### Overlap 5: Error envelope and error-code registry

Touches: all API and LiveView boundaries.  
Shared primitive: error mapper from Ash/domain errors to stable, user-safe errors.

### Overlap 6: Outbox and background jobs

Touches: notifications, webhooks, refunds, payouts, reconciliation, exports, event updates.  
Shared primitive: outbox + Oban conventions.

### Overlap 7: Order snapshot

Touches: pricing, checkout, entitlements, fees, VAT/tax, discounts, attribution, refunds, chargebacks, finance reports.  
Rule: never recompute historical economics.

## 12A. Planning catalogue lint rules for future automation

Before any row is imported into Linear or handed to a coding agent, the planning catalogue MUST pass these checks:

1. **No duplicate IDs:** every `TB-*`, `VS-*`, `CI-*`, `PP-*`, `OPS-*`, and `FUT-*` ID must be unique.
2. **No self-dependencies:** a row's `Hard prerequisites` field MUST NOT contain its own ID.
3. **No unknown ID references:** explicit IDs in dependency fields must resolve to known rows or known contract IDs.
4. **No dependency cycles:** the `Hard prerequisites` graph must be a DAG.
5. **No `FR-TBD` in coding-ready packs:** `FR-TBD:*` is allowed only in this catalogue, not in executable Feature Planning Packs.
6. **No candidate-only resources/actions in coding-ready packs:** `definitely_required_resources` and `definitely_required_actions` must be resolved.
7. **No non-canonical finance aliases:** `LedgerJournal` and similar aliases are forbidden unless defined by a contract.
8. **No UUID string sorting:** any crypto/signature/tie-break/apportionment ordering must use raw 16-byte unsigned lexicographic UUID ordering.
9. **No generic CMS drift:** event sales content slices must not become a CMS/editorial platform without a future FR-1 entry and contract expansion.
10. **No direct coding from this catalogue:** only Feature Planning Packs may become coding-agent prompts.
